# AutoCage decision log

**Status (2026-10-15):** M0–M3.6 implementation and declared evaluations are complete. M3 remains historically **INCONCLUSIVE** because RR03 did not produce a validated narrow policy. M3.5's same-source patch repeats did not establish routine workflow value. M3.6 found the pre-execution suggestions identical to competent static profiles on eight workflows and 16 source/revision cases, with equal utility and canary outcomes; authoring-effort improvement was not measured. Decision D33 supersedes D32: retain profiles as experimental infrastructure and pivot the main contribution to agent-containment evaluation. See the [M3.6 report](../experiments/m36-preexecution-value/REPORT.md).

| ID | Decision | Rationale | Evidence that could change it |
|---|---|---|---|
| D1 | Optimize verifier-validated policies only inside a developer-approved ceiling; do not infer authorization. | Requests, traces, and LLM judgments cannot establish authority. A verifier is utility evidence only. | Formal authorization model and adversarial evidence for safely broadening inference. |
| D2 | MVP narrows staged-workspace writes only, with distinct exact-file inode and directory-entry operations. | M0 validated readonly base, exact-file in-place writes, recursive directory writes, and nested readonly precedence. M2 also tested an owner-permitted exact-file mode change. Exact-file mounts do not permit create/unlink/rename/atomic replacement; those operations require directory authority. | Real tasks show the representable write vocabulary cannot improve task utility and reduce writable surface. |
| D3 | Bubblewrap remains the first backend; namespace isolation is mandatory and delegated to it. Ubuntu 24.04 setup loads only the distro `bwrap-userns-restrict` profile and keeps the global userns restriction enabled. | The default image denied UID-map writes; the official package profile fixed namespace setup and passed the complete 41-check M0 harness. | A supported image fails the checked profile/namespace preflight or a different backend demonstrates a smaller, equally testable trusted boundary. |
| D4 | No networking in initial runner. | One shared namespace cannot distinguish inference requests from shell traffic. Allowing a model endpoint lets reachable processes send data to it. | Supported agent tool protocol or broker that separates agent identity from tool processes with enforceable isolation. |
| D5 | First real-agent experiment uses local inference in the same private network namespace. | Free/reproducible and avoids API credentials/egress; local hardware/model quality constrain it. Codex and Aider document local Ollama paths. | End-to-end Linux experiment proves infeasible on typical developer hardware. |
| D6 | Stage by copying; Git worktree is not the security boundary. | M0 demonstrated a raw bind of a source hard-link alias exposes and can mutate the outside inode. Copying bytes breaks the alias but does not redact content already present via a source hard link. | Tested immutable/COW staging with equivalent isolation and much lower cost. |
| D7 | No OverlayFS requirement in v1. | Unprivileged support varies by kernel/filesystem; ordinary copy is easier to reason about. | Measured copy overhead is unacceptable. |
| D8 | Defer Landlock/seccomp. | They add a second compiler/kernel ABI surface; seccomp does not provide path/hostname policy. | Canary identifies an invariant requiring one, or measured benefit is substantial. |
| D9 | No SQLite/graph database; TOML policy and JSON records. | Single-user CLI has no demonstrated database need. | Actual concurrent/query workload warrants it. |
| D10 | Verifier pass is not security proof; canaries are independent. | Repository tests may be incomplete or modified. | None; only oracle provenance/coverage can improve. |
| D11 | AuthBench is the first external benchmark candidate, subject to audit. | It has task-level permission scoring and constrained replay; Docker/Harbor setup and labels need review. | License, reproducibility, or policy-model mismatch. |
| D12 | Originality is conditional on early optimizer results. | AuthBench, OpenShell, nono, Sandlock, and aa-genprof overlap parts of the problem. AutoCage's proposed delta is budgeted verifier-guided narrowing and run evidence, not sandboxing itself. | Equivalent competitor feature or trivial measured policy reduction. |
| D13 | Mac is not an enforcement environment; Lima's Apple Virtualization guest is the dev target. | Homebrew 6.0.14 and Lima 2.2.1 on macOS 26.6.2 ARM64; VM has `mounts: null`. M0 passed inside Ubuntu 24.04.5 ARM64. | A reproducible Linux-on-Mac path fails a required invariant or host sharing cannot remain disabled. |
| D14 | Never disable Ubuntu's global AppArmor unprivileged-userns restriction or make Bubblewrap setuid. On the tested image, use only the official distro profile and fail closed if it is unavailable or unenforced. | The default profile denied `/proc/<pid>/uid_map`. Ubuntu `apparmor-profiles`/`apparmor-utils` 4.0.1really4.0.1-0ubuntu0.24.04.8 supplied the inspected profile; `apparmor_restrict_unprivileged_userns` remained `1`, both Bubblewrap profiles enforced, and the full M0 suite passed. | The official profile fails a required property on another supported kernel/package revision. |
| D15 | M0 passed on the measured guest; M1 is implemented and limited to the minimal fail-closed runner. | M0 has 41 PASS. M1 passed 22 unit tests, 6 Linux integration tests, rustfmt check, and release build on the same isolated guest. The [M1 report](../experiments/m1-runner/REPORT.md) records the command coverage and boundaries. | A reproducible rerun fails, or a changed implementation cannot preserve a validated invariant. |
| D16 | An exact-file Bubblewrap write grant permits in-place inode operations but not directory-entry changes. Directory-entry operations need a writable parent directory; nested readonly file mounts can protect selected children. | M0 validated content write, create/unlink/rename/atomic-replace behavior, and nested mount precedence. M2 verified an owner-permitted mode change on an exact-file grant. A file-only grant does not support common atomic-save behavior. | A different tested mount construction provides equivalent exact-file namespace operations without widening siblings. |
| D17 | The supervisor must close unapproved file descriptors before executing Bubblewrap. | M0 showed an explicitly passed synthetic host FD is readable inside the child; a close-fds launch blocks it. Bubblewrap is not an FD scrubber. | An audited Bubblewrap behavior change or an equally strong kernel-enforced FD isolation design. |
| D18 | Every sandbox launch requires `--disable-userns --assert-userns-disabled`. | M0 control showed nested userns works when omitted and is rejected when set. Ubuntu's child profile itself allows userns, so the Bubblewrap seccomp restriction is needed. | A future validated layer prevents nested userns independently and removes the need for these flags. |
| D19 | M1 used one fixed recursive read/write grant for the copied workspace and did not compile exact-file or subdirectory rules. | This established a simple utility baseline without implying a narrow policy search. M0 showed exact-file mounts permit in-place inode operations only, while common atomic saves need parent-directory authority. M2 implements those additional grant shapes. | A tested mount change supports more precise directory-entry operations without widening siblings. |
| D20 | M1 mounts `/usr` read-only plus `/bin`, `/sbin`, `/lib`, and `/lib64` aliases, and omits `/etc`. | The M0 Python/pytest fixture passed both with and without `/etc`; M1's Python command and pytest verifier passed with `/etc` absent. This limits visible runtime files but may not support arbitrary project toolchains. | A reproducible task fails because a specific `/etc` file is needed; add only a tested read-only runtime exception. |
| D21 | M1 accepts only Ubuntu 24.04 ARM64 with Linux 6.8+, the enforced distro Bubblewrap AppArmor child profile, non-setuid root-owned Bubblewrap, and a trusted root-owned `diff` utility. | This matches the only Linux configuration validated so far and makes check/run refuse incompatible or tampered runtime binaries rather than guessing. | A second explicitly tested distribution/kernel matrix justifies broadening preflight. |
| D22 | M2 policy cost v1 counts weighted writable regular files plus 10 per existing directory entry writable under recursive directory grants; raw counts remain separate. | Prevents a single broad recursive rule from appearing safer than several exact-file grants. The 1/10 weights are explicit heuristics, not calibrated risk probabilities. The frozen 22-task evaluation met the 25% reduction threshold. | Empirical exploit/exposure calibration or a declared alternative objective that better predicts practical risk. |
| D23 | Promote a narrowed policy only after three fresh source-snapshot replays pass both the fixed verifier and security checks; include all three in the replay cap. Return the verified broad ceiling when search is inconclusive. | M2 had 20 three-pass narrowed policies and two root-entry tasks where Bubblewrap required root directory-entry authority. Denials did not expand candidates. | Stochastic-agent evidence may require a larger statistical protocol; never remove the fresh-pass requirement solely to lower latency. |
| D24 | Store argv digests and counts, never raw argument values, under explicit `--record-contract`; keep the contract mode 0400 and bind it to the run record, executable hashes, source identity, verifier roots, ceiling, and runtime facts. | Tuning needs exact replay identity, while CLI args may contain prompts or secrets. Tuning therefore requires callers to resupply the same argv, which is compared by digest. Hashes do not protect low-entropy values from guessing. | A replay interface that retains exact semantics with stronger protection than caller-resupplied argv digests. |
| D25 | Do not claim hierarchical search is more efficient than greedy/random removal. Retain all strategies as experimental arms; reassess the CLI default before a user-facing release. | In M2, hierarchical had median 7 replays versus 6 for fixed greedy and random, same median cost, and 49 rejected candidates versus 30/29. It did not establish a search-structure advantage. | A new predeclared benchmark shows a repeatable held-out replay/cost advantage without lower utility or canary coverage. |
| D26 | M2 v1 seeds file-content grants from same-path regular-file deltas; it does not infer replacement semantics from inode identity. | The initial and final content/mode manifests cannot distinguish an in-place edit from replacing that file's directory entry. The changed-file baseline failed the atomic-replacement task; bounded verifier search recovered it. Keep this observation limit explicit. | Repeated real-task false denials justify recording stage-local inode identity or operation evidence, with source hashes kept stable across fresh copies. |
| D27 | Replay contracts require one or more declared read-only verifier roots; existing workspace paths named in verifier argv must be covered by those roots after sandbox-path normalization. | M3 hardened a gap where a caller could record a verifier path without protecting its source input. The contract fingerprints the declared roots and rejects explicit uncovered workspace paths. The caller still must declare implicit imports, plugins, and auto-discovered config; completeness is not inferred. | A principled way to discover and freeze all verifier inputs without executing untrusted code outside the sandbox. |
| D28 | Keep exact-run-contract invalidation; do not add cross-task or cross-snapshot learned-policy reuse without a separate, developer-authorized workflow identity. | M3 binds source snapshot, command digests, verifier roots, runtime, backend, environment, timeout, and ceiling. M3.5's explicit exact-snapshot repeats passed, but all tested source/command/runtime drift was rejected; research-only RR01 shadows do not authorize reuse. | A predeclared profile experiment demonstrates useful reuse across controlled workflow repetitions without increasing false denials or weakening production checks. |
| D29 | M3 does not establish hierarchical search superiority or general real-agent usefulness. | On seven held-out tasks, F and D/E had the same 76.2% median full-corpus reduction; F used 11 median replays versus 8. No local/stochastic agent or scale series was tested. | Larger predeclared real-repository results showing stable utility and a reproducible cost advantage under equal budgets. |
| D30 | Keep exact source/command/verifier/runtime checks; do not reuse learned policy evidence across source changes. The repeated cases re-ran source-changing patch transformations from identical parents; they did not establish recurring test/build workflow value. | D31 | Keep hierarchical search experimental; use greedy as the simpler candidate for a future default unless a frozen evaluation shows robust advantage. | M3.5 real workflows showed the same 88.1% conditional median and 76.2% full-corpus median for D/E/F; F used 82 replay executions versus 76 for D/E. The synthetic scaling matrix showed a clustered-layout benefit but a dispersed-layout penalty. | A new held-out real-workflow study establishes a repeatable total-cost advantage across both clustered and dispersed requirement layouts. |
| D32 | Do not begin M4 real-agent integration yet. Compare post-run optimization with a developer-authored pre-execution workflow profile and static policy on actual recurring commands first. The selected canary arm shows potential but not sufficient product value. | D33 | Keep deterministic pre-execution profiles as experimental infrastructure; pivot the primary research contribution to agent-containment evaluation. Static, authored, and suggested grants were identical; all blocked the same 96/96 staged canary writes. Suggestion generation took 4.5 ms median with zero full-task replays, but did not save measured user effort. Greedy post-run optimization reached the same profiles at four task replays per workflow. The project owner approved the architecture before production implementation. Changes to D1–D5 or D11–D12 require updating this log and evaluation criteria first.

## Ranked risks and unresolved evidence

1. **High severity, medium-to-high likelihood — no hard aggregate resource limits.** A fork/memory/CPU bomb can affect the Linux host even when filesystem and network policy work. Until delegated cgroup v2 or outer-VM limits are validated, limit adversarial evaluation to disposable resource-limited VMs and do not claim availability isolation.
2. **High severity, medium-to-high likelihood — replay overhead and exact identity may erase practical usefulness.** M3.5 measured 4.57 seconds median incremental scripted tuning versus a 0.299-second static run; its 10-repeat amortized-overhead gate failed. The arithmetic allocation over roughly 16 hypothetical repetitions is not a latency break-even: no later-run speedup was measured. Agent-model replay cost was not measured and could be much higher. M3.6 found that pre-run suggestions add no measured advantage over a competent static policy; the production contract correctly rejects changed sources for learned evidence.
3. **High severity, medium likelihood — AppArmor policy/profile availability varies across Ubuntu images.** The official Noble profile passed on the tested guest, but other kernels/package revisions may differ. Keep the global restriction enabled; preflight must fail closed if the expected profiles are absent or unenforced.
4. **High severity, medium likelihood — verifier manipulation or incompleteness creates false confidence.** Keep evaluation verifiers outside the stage, fingerprint/protect developer verifier inputs, and never use verifier success as a security score.
5. **Medium severity, high likelihood — local model quality and hardware make the real-agent example slow or weak.** Keep it optional; publish hardware/model details; do not use it as evidence for the deterministic optimizer claim.
6. **High severity, low-to-medium likelihood — future remote model support requires a network/credential boundary that is out of scope.** Do not add domain allowlists as a shortcut. Re-evaluate integration with OpenShell or nono, or a real agent tool-broker protocol, before committing to it.
7. **Medium severity, medium likelihood — staging and runtime mounts vary by distribution and filesystem.** Test exact target kernels, measure copy overhead, and keep the supported platform narrow.
8. **High strategic severity, high likelihood — algorithmic originality remains unproven.** AuthBench overlaps permission generation plus constrained replay; Sandlock overlaps Linux agent isolation. M3.5 found no consistent hierarchical advantage: clustered synthetic atoms favor it, dispersed atoms penalize it, and real workflow replay totals matched or exceeded simpler strategies. Do not claim a distinct algorithmic advantage.

The M0–M2 gates and M3 record-hardening checks passed their scoped criteria on the named guest. M3's real-repository result remains historically inconclusive. M3.5's individual controls and exact-source repeats passed, but its policy-value and amortized-overhead gates failed. M3.6 showed that selected pre-execution suggestions can preserve utility and block tested staged writes, but no better than competent static policies; human authoring time was not measured. Next research should evaluate containment of untrusted agent/tool behavior with deterministic fixtures first, separately measuring utility and security. Remaining evidence gaps include real-agent behavior, write-surface measurement for future descendants, resource-exhaustion isolation, and behavior on other Linux configurations.
