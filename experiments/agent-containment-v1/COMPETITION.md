# Targeted comparison: security-evaluation infrastructure

Reviewed 2026-10-17 against primary documentation, source repositories, and papers. This is a scope check, not a broad landscape survey.

| Project | What it already provides | Implication for AutoCage |
|---|---|---|
| [Inspect AI](https://inspect.aisi.org.uk/) / [Inspect SWE](https://inspect.aisi.org.uk/agents.html) | A general evaluation framework with datasets, solvers, scorers, `.eval` logs, external coding-agent runners including Codex CLI, and an extension API for sandbox providers. | Reuse Inspect for evaluation orchestration, task records, repeat management, and report viewing. AutoCage's distinctive contribution should be its local Linux enforcement/evidence backend, not another task/eval framework. |
| [AgentDojo](https://github.com/ethz-spylab/agentdojo) (NeurIPS D&B 2024) | Paired user tasks and prompt-injection attacks in tool-use environments, with separate utility/security scoring and defense comparisons. | Its task model is API/tool environments rather than OS-enforced code workspace mutations. Reuse paired-task and utility/security reporting conventions; do not claim paired injection evaluation as novel. |
| [BoundaryBench](https://github.com/boundary-bench/boundary-bench) | Directly benchmarks coding-agent harnesses on Terminal-Bench tasks under hardened policies, measuring task success and cost. It is already an Inspect extension and writes Inspect logs. Its published quickstart uses OpenRouter and Daytona credentials. | This is the closest product overlap. A general “agent runs under two sandbox policies and compare success” CLI would duplicate it. AutoCage's possible niche is a local/free Inspect sandbox provider with machine-observed Bubblewrap denials and independent staged canary evidence; this needs validation against BoundaryBench's enforcement-probe and analysis features. |
| [AgentSec-Bench](https://github.com/Santhosraj/AgentSec-Bench) | Inspect-based security challenges spanning offensive, defensive, secure-coding, and harness-safety tasks; its repository describes isolated, no-egress targets for security axes and an agent bridge for harness comparisons. | Reuse its challenge/scoring ecosystem if the task becomes model resistance or secure-code capability. It is not a reason to implement another general challenge framework. |
| [ContainmentBench](https://arxiv.org/abs/2607.23999) (arXiv preprint, 2026-07-27) | A trace-based post-injection containment protocol separates endpoint policy outcomes, logged propagation/trajectory, recovery evidence, and authorized utility. | The planned separation between agent behavior, attempted tool action, OS denial, and utility is already a research convention. AutoCage can contribute real OS syscall and filesystem evidence, but must not claim the metric decomposition itself as original. |

## Focused adjustment

Build a **custom Inspect sandbox provider/evidence adapter** around the existing AutoCage Rust boundary rather than an independent evaluation platform. Keep scenario authoring as Inspect tasks and scorers; have AutoCage return structured records for its actual namespace/mount checks and a small number of explicit canary outcomes. Store trace source/coverage and distinguish “not observed” from “no attempt.” Avoid a general run comparison engine unless Inspect cannot represent the required paired-policy flow.

BoundaryBench already establishes the broad capability-under-policy question. M4 demonstrated a no-egress Aider/Ollama/Qwen local path and machine-observed Bubblewrap enforcement, but its one real-agent pair saw no protected-write attempt, so it provides no model-resistance result. The deterministic controller verifies the evidence path; it does not yet prove differentiation over Inspect's sandbox extensions or BoundaryBench's enforcement probe. The evidence supports a thin Inspect integration experiment, not a standalone evaluator.
